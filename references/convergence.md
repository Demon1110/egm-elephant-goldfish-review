# 裁决与收敛

评审产出的是**建议**，裁决权在人。这一阶段最容易出两种事故：把意见当结论、把收敛当“改到没人再说话”。

## 一、四类裁决

| 裁决 | 什么情况下用 | 必须写清 | 禁止 |
| --- | --- | --- | --- |
| PROPOSE FIX | 问题成立，改法明确 | 改哪一节、改成什么、改完怎么验证 | 只写“已修复”不写改法 |
| CONTEST | 问题不成立，或依据不成立 | 引用评审者能读到的证据（章节、代码行、清单文件） | 用“我们讨论过”“你理解错了”当理由 |
| ESCALATE | 需要超出设计者权限的判断（预算、组织、合规、优先级） | 需要谁定、定之前卡住什么 | 把能自己定的问题往上推 |
| DECLINE | 本轮不改，接受风险 | 风险是什么、谁接受、什么时候复查 | 用它清空台账 |

硬规则：

1. **理解性缺口不许 CONTEST**。文档没写清就是没写清，读者看不懂不是读者的错。只能 PROPOSE FIX（补写）或 ESCALATE（这项要人定）。
2. **CONTEST 必须有证据**。证据必须是金鱼能读到的东西，否则改判 ESCALATE。
3. **严重度不许悄悄改**。要调整级别，在台账的“理由/证据”里写“原 Major → Minor，理由：……”，不能直接覆盖。
4. **DECLINE 必须留复查时机**，不能写“以后再说”。

## 二、收敛的定义

```
clean(第 N 轮) = 第 N 轮不存在“未 settled 的 Blocker 或 Major”
```

两个细节：

- **判定在应用本轮修复之前**。先按本轮报告算出 clean/dirty，再改文档。改完再判等于自己给自己发通行证。
- **Minor / Nit 不必全部清零**，允许带着已知小问题进入实现，但要在交接边界里列出来。

收敛条件（三条同时满足）：

1. 连续 **两轮** clean；
2. 总轮次 **不超过 5 轮**；
3. 台账里没有 `open` 或 `reopened` 状态的 Blocker / Major。

不满足就继续下一轮；到第 5 轮仍有分歧，**停止自动化，交人决定**——继续跑只会把分歧磨成措辞。

## 三、跨轮记账

- `settled` 的 finding **跨轮保持**，后续轮次不得重复提出同一个问题；若被重新提出，视为新 finding 还是旧账，看是否同一根因。
- 已修复的 finding 若被后续评审者再次提出，**重新打开**（状态改 `reopened`），不能以“上一轮已经改过”驳回。
- 每轮结束后更新台账的四张表：裁决台账、收敛记录、未决问题。收敛记录里填本轮 B/M/Minor/Nit 数量和是否 clean。
- `scripts/egm_kit.py check` 会把“未进台账的 finding”“台账状态非法”“CONTEST 无证据”判为错误。

## 四、churn（来回改）

出现下面任一情况，判定为 churn：

- 要撤销上一轮的修复，才能消掉本轮新提的问题；
- 同一处连续两轮被要求往相反方向改；
- 为了消 finding 而把方案改成了另一个方案，且没有重新走 Step 5。

处理：**停止自动裁决，把两轮报告和台账一起交给人**，由人选择保留哪个方向、或回退到哪一版。churn 不是评审质量问题，通常是设计本身没定下取舍。

## 五、假收敛的六种样子

发现以下任一情况，即使脚本判定通过，也不能进入交接：

1. 改的是措辞不是设计（把“尽最大努力”改成“尽力而为”）；
2. 把两条 Major 合并成一条 Minor；
3. 用 DECLINE 把台账清空；
4. 派了同一个会话里的“自己”当评审者，报告里写着 complete；
5. 每轮都由同一个金鱼重复上轮意见，没有新视角；
6. 第 5 轮“刚好”clean，但第 1–4 轮的 Major 都还是 `open`。

## 六、收敛之后

1. 把最终草案版本号写进 `handoff_boundary.md` 的“依据版本”；
2. 台账里所有 Blocker / Major 必须 `settled`，剩下的 Minor / Nit 列进交接边界的“已知小问题”；
3. 请人明确批准（写进 `handoff_boundary.md` 的“人已批准”与 `manifest.json` 的 `isolation.approved_by_human` 只用于隔离，不用混淆）；
4. 批准后才进入实现相：实现 agent 只能在 Target Scope & File Boundary 内写。
